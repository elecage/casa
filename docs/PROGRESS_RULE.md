# 진전 판정 규칙 — 확정 설계 (2026-08-19)

**결정**: 진전을 하나의 예/아니오로 묻지 않고 **세 갈래(앎·산출·증거)**로
나눠 각각 판정한다. 유저 승인 2026-08-19.

이 규칙이 `docs/BADNESS_SIGNALS.md`의 헛돎·검증·에러대응 계열 전체의 전제다.
그래서 단일 최대 병목이었다.

---

## 1. 왜 하나로는 안 되는가

진전을 한 가지로 정의하려 하면 바로 모순에 부딪힌다.

- **읽기는 아무것도 바꾸지 않는다.** 상태 변화로 정의하면 조사가 전부
  "진전 없음"이 된다. 신중한 세션이 헛도는 세션으로 찍힌다.
- **엉뚱한 파일을 고치는 세션도 매번 상태를 바꾼다.** 상태 변화를 진전으로
  치면 가장 큰 낭비 유형을 통째로 놓친다.

두 번째가 결정적이다. 비교 논문에서 **낭비가 가장 큰 실패 유형이 "엉뚱한
것을 고치고 있음"**이었다 — 실패 궤적의 24%, 전체 낭비의 39%, 그 뒤로
21스텝이 더 간다(`docs/COMPARISON_RUNTIME_MONITOR.md`). 이 상태에서 세션은
계속 편집하고 결과도 매번 달라지므로, 진전을 하나로 뭉치는 모든 정의가
"진전 있음"으로 판정한다.

세 갈래로 나누면 보인다:

| | 앎 | 산출 | 증거 |
|---|---|---|---|
| 엉뚱한 곳 수리 | 0 | 계속 + | **0 (확인 결과가 그대로)** |

고치고는 있는데 증거가 안 움직인다. 나눠야 보이는 신호다.

## 2. 세 갈래의 정의

호출 하나마다 세 값을 낸다.

| 갈래 | 묻는 것 | 값 |
|---|---|---|
| **앎** | 전에 모르던 정보를 봤는가 | 0 또는 +1 |
| **산출** | 프로젝트가 실제로 바뀌었는가 | −1, 0, +1 |
| **증거** | 확인 결과가 달라졌는가 | 0 또는 +1 |

### 2.1 앎 (knowledge)

세션이 새로 알게 된 것이 있으면 +1.

| 호출 | +1 조건 | 0 조건 |
|---|---|---|
| `Read` | 처음 보는 경로, 또는 알던 경로의 처음 보는 구간 | 이미 읽은 경로·구간 재열람 |
| `Grep` `Glob` `LS` | 정규화한 결과 집합이 이전의 동등 질의와 다름 | 같은 질의에 같은 결과 |
| 읽기 전용 셸 | 정규화한 출력 해시가 처음 | 같은 출력 재등장 |
| `WebFetch` `WebSearch` | 처음 보는 URL/질의 | 반복 |
| **에러 결과** | 정규화한 에러 서명이 처음 | 같은 에러 재등장 |

읽기 전용 셸 판정은 기존 `transcript._SHELL_EXPLORE_PREFIXES`를 쓴다.

**에러를 앎으로 취급하는 이유**: 처음 보는 에러는 새 정보다. 같은 에러가
반복되면 정보가 아니다. 이 규칙이 목록의 "에러 후 행동 변경률"과 자연스럽게
맞물린다.

### 2.2 산출 (artifact)

프로젝트 상태가 실제로 바뀌었으면 +1, **전에 있던 상태로 되돌리면 −1**.

| 호출 | 판정 |
|---|---|
| `Edit` `Write` `MultiEdit` `NotebookEdit` | 경로의 내용 해시가 **처음 보는 상태**가 되면 +1 |
| 같은 도구, 결과가 **이 세션에서 이미 본 상태** | **−1 (되돌림)** |
| 같은 도구, 내용 변화 없음 | 0 |
| 파일 생성·삭제 | +1 |
| 상태를 바꾸는 셸 명령 | +1, 단 그 경로의 추적을 **신뢰 불가**로 표시 (§5) |

되돌림을 0이 아니라 −1로 세는 이유는 갈팡질팡이 0으로는 안 드러나기
때문이다. 고쳤다 되돌리기를 반복하면 산출 합계가 0 근처에 머문다.

### 2.3 증거 (evidence)

**확인 성격의 호출에만** 적용한다. 판정 대상은 기존
`metrics._is_test_run` / `metrics._is_aux_check`가 잡는 호출이다.

| 조건 | 값 |
|---|---|
| 정규화한 출력이 **이 세션에서 처음 보는 것** | +1 |
| 이미 본 출력 | 0 |

"같은 테스트를 돌렸는데 결과가 그대로"가 0이 되는 것이 핵심이다.

**2026-08-19 수정 (구현 중 단위 테스트가 발견, 데이터 확인 전)**: 원안은
*명령*을 기준으로 삼아 "그 명령의 첫 실행이면 +1"이었다. 그러면 확인 명령을
조금씩 바꿔가며(`-k` 선택자를 매번 달리하는 식) 같은 답을 계속 받아도 매번
새 증거로 세어진다. 에러 축에서 이미 닫은 것과 같은 구멍이다 — **정보는
돌아온 내용이지 입력한 명령이 아니다.** 그래서 판정 기준을 결과로 옮겼다.
경보 문턱은 건드리지 않았다.

## 3. 파생 지표

세 갈래에서 병리 신호를 뽑는다. 전부 앞에서부터 순서대로 계산되고,
다른 세션이 필요 없다.

| 신호 | 정의 | 알림 문구 예 |
|---|---|---|
| 완전 정지 연속 길이 | 앎·산출·증거가 모두 0인 호출의 연속 개수 | "14번째 호출째 아무것도 안 바뀌고 있습니다" |
| 조사 마비 | 앎은 계속 +인데 산출이 한 번도 없음, 길이 N 초과 | "40번 읽었는데 아직 한 줄도 안 고쳤습니다" |
| 증거 정지 | 산출 +가 있었는데 그 뒤 확인 호출 m개가 전부 증거 0 | "12번 고쳤는데 확인 결과가 그대로입니다" |
| 되돌림 횟수 | 산출 −1의 누적 | "고쳤다 되돌리기를 5번 했습니다" |
| 진전 밀도 | 최근 창에서 세 갈래 합이 0 초과인 호출의 비율 | 보조 |

**알림 문구가 구체적인 것이 설계 요구다.** 비교 논문에서 "실패한 검사의
이름만 알려주기"가 회복률 45%로 그냥 재실행(16%)의 세 배였다. 외부 앱은
사람에게 알리는 것이 전부이므로, 사람이 판단할 수 있는 말이 나와야 한다.

## 4. 정규화 규칙

같은 일을 두 번 해도 출력이 미세하게 다르면 "새것"으로 보인다. 해시 전에
아래를 지운다.

**지우는 것 (알려진 변동 요소만)**:
- 날짜·시각 표기 (ISO 8601, `HH:MM:SS`, 로케일 날짜)
- 소요 시간 (`1.23s`, `450ms`, `0:01:21`)
- 절대 경로 중 프로젝트 루트·임시 디렉토리 부분 → 자리표시자
- 메모리 주소 (`0x[0-9a-f]+`), 프로세스 번호
- 터미널 색상 제어 문자
- 줄 끝 공백, 줄바꿈 방식(CRLF/LF)

**절대 지우지 않는 것**: 일반 숫자. `3 failed, 5 passed`의 숫자를 지우면
증거 갈래가 통째로 죽는다. **정규화는 알려진 변동 패턴만 대상으로 하고,
숫자 일반을 뭉개지 않는다.**

**검증 방법**: 이미 모은 127세션에 돌려 두 방향의 오류율을 본다 — (a) 실제로
다른 결과가 같은 해시가 되는 비율, (b) 같은 결과가 다른 해시가 되는 비율.
**새 수집이 필요 없다** (수집 잠금 유지).

## 5. 기억 범위

| 갈래 | 기억 | 근거 |
|---|---|---|
| **앎** | 문맥 압축이 일어나면 **초기화** | 압축은 세션이 정당하게 잊은 것이다. 파서가 이미 압축 시점을 기록한다 (`ToolCall.after_compaction`) |
| **산출** | 초기화하지 않음 | 파일 상태는 세션이 기억하든 말든 실재한다 |
| **증거** | 초기화하지 않음 | 같은 이유 |

이 구분이 중요하다. 압축 후 같은 파일을 다시 읽는 것을 "헛돎"으로 찍으면
부당한 헛경보가 된다. 반면 압축 후 같은 편집을 되풀이하는 것은 여전히
되돌림이다.

## 6. 셸 사각지대 — 정직하게 남기는 한계

`sed -i`나 리다이렉션으로 파일을 고치면 편집 도구를 거치지 않으므로
**무엇이 어떻게 바뀌었는지 기록만으로는 알 수 없다.** 이 프로젝트는 전에
셸 사각지대 때문에 지표를 오판한 적이 있고 그래서 셸 인지 파서를 만들었다.

**대응**:
- 상태 변경 셸 명령은 산출 +1로 세되, 그 시점 이후 **해당 경로의 내용 추적을
  신뢰 불가로 표시**한다. 되돌림(−1) 판정은 신뢰 불가 경로에서는 하지 않는다.
- 세션마다 `state_confidence` = 구조화 도구를 거친 변경의 비율을 함께 낸다.
  이 값이 낮으면 산출 갈래의 해석에 주의가 필요하다는 뜻이다.

없는 척하지 않고 표시하는 쪽을 택한다.

## 7. 이 규칙이 하지 않는 것

- **LLM 심판 없음.** 전부 결정론적 비교와 해시.
- **다른 세션 필요 없음.** 세션 자기 자신의 앞부분만 본다 — 외부 앱의
  콜드 스타트 문제와 기준선 이동 문제를 둘 다 피한다
  (`docs/COMPARISON_RUNTIME_MONITOR.md` 갭 1·2).
- **과제 정의 필요 없음.** 임의의 사용자 프로젝트에서 설정 없이 돈다.

## 8. 구현이 요구하는 변경

**파서**: `src/casa/transcript.py`가 현재 도구 결과에서 `is_error` 한 비트만
꺼내고 내용을 버린다. 결과 본문을 보존해야 한다.

확인된 사실 (2026-08-19): 트랜스크립트에 **도구 결과가 내용까지 전부 기록돼
있다.** 한 세션에서 도구 호출 132건에 결과 131건이 있었고 129건이 문자열
본문이었다(나머지 2건은 리스트 형태). 형태 둘 다 처리해야 한다.

**메모리**: 결과 본문을 전부 들고 있으면 안 된다(세션당 수 MB). 정규화한
해시만 보관한다.

## 9. 검증 계획

1. **정규화 오류율** — §4의 두 방향, 기존 127세션.
2. **퇴화 사례 탐지** — `results/main2/ml-shift-sonnet`의 세션 하나(도구 호출
   248회, 동일 호출 38회 반복, 86분 후 시간 초과, 규칙 위반 58건)가 실제로
   잡히는가. 잡힌다면 몇 번째 호출에서 잡히는가.
3. **헛경보** — 같은 조건의 정상 세션 6개에서 경보가 뜨지 않는가.
4. **끊기 대 계속** — `docs/RESTART_EVALUATION.md`.

전부 기존 데이터로 가능하다. 수집 잠금을 풀 필요가 없다.
