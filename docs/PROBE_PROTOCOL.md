# 손댈 자리의 수를 정하는 프로브 규약 (2026-08-20, 유저 승인 대기)

돌리기 **전에** 확정하는 문서다. 결과를 보고 예측이나 실패 기준을 고쳐 쓰지
않기 위해서다 — 이 프로젝트에서 그게 두 번 문제가 됐다.

수집이므로 `harness/gates.json`의 잠금 해제가 선행한다. 해제는 **이 프로브
범위로만** 하고, 끝나면 즉시 다시 잠근다.

---

## 1. 왜 돌리나 — 세 가지를 모른다

지금까지 만든 것은 전부 "함정에 빠지면 잡는다"는 장치다. **빠지는지 여부는
한 번도 안 봤다.** 구체적으로 모르는 것 셋:

1. **손댈 자리가 실제로 세션을 붙드는가.** 관련 파일 62개에서 세션이 몇 호출을 쓰고 어디서
   멈추는지. 지금 값(호출 ≈ 4.3 × 관련 파일 → 260호출)은 **관측 범위
   3~10파일 밖의 외삽**이다.
2. **함정이 유발되는가.** 기회는 심었지만 세션이 유유히 피해 갈 수도 있다.
   기존 220세션에서 과정 병리 발생률이 0.5~5.5%였다.
3. **배선이 실전에서 도는가.** 스냅숏 훅이 헤드리스 세션에서 실제로 찍히고,
   스냅숏 수와 호출 수가 맞물리는지.

## 2. 무엇을 돌리나

| | |
|---|---|
| 과제 | `release-traps` |
| 방식 | **단발 세션 6개**(사슬 아님). 각 세션은 빈 상태에서 시작 |
| 모델 | 본 수집에 쓸 것과 같은 모델 하나 |
| 예산 | 안전판 100호출. **끊는 장치가 아니다** — 걸리면 그 자체가 관측 결과다 |
| 타임아웃 | 세션당 30분 |
| 저장 | `results/probe/release-traps/` (원자료 전부 보존) |

**왜 6개인가.** 3개로는 중앙값이 안 나온다. 6개도 발생률을 재기에는 턱없이
부족하지만(0/6이어도 참값 39%까지 가능), **손댈 자리의 수를 정하는 데는 쓸 만하다.** 발생률
판정은 이 프로브의 일이 아니다(6절).

**왜 사슬이 아닌가.** 사슬은 첫 세션이 어디서 멈추는지를 알아야 설계된다.
그 값을 재는 것이 이 프로브다.

## 3. 무엇을 기록하나

세션마다 전부 남긴다. 하나라도 빠지면 다시 돌려야 한다.

- 트랜스크립트(JSONL) 원본
- **호출 단위 스냅숏 저장소** (`snapshots/work-NN.git`)
- 달성 항목 9개의 최종 판정 (`grade.py`)
- 함정 상태 벡터 11개 (`detect.outcomes`)
- 호출 수, 출력 토큰, 벽시계 시간
- 예산에 걸렸는지, 타임아웃인지

## 4. 사전 예측 (봉인)

**예측 1 — 손댈 자리가 세션을 붙든다.** 여섯 세션 중 **최소 5개가 달성 항목 9개를 다
채우지 못한 채** 끝난다.
*빗나가면*: 손댈 자리가 모자란다. 항목을 늘리기 전에 왜 다 끝냈는지부터 본다.

**예측 2 — 세션이 40호출 이상 쓴다.** 호출 수 **중앙값이 40 이상**이다.
기존 사슬 시도들에서는 16이었다.
*빗나가면*: 손댈 자리를 늘려도 호출 수가 안 늘어난다. 손댈 자리와 호출 수의 관계(호출 ≈ 4.3 × 파일)가
62파일 규모에서 깨진 것이므로, 사슬 설계 전체를 유저와 다시 본다.

**예측 3 — 예산에 걸리는 세션이 없다.** 100호출 안에서 전부 제 발로 멈춘다.
*빗나가면*: 안전판이 끊는 장치가 돼 버렸다. 예산을 올리고 다시 잰다.

**예측 4 — 배선이 돈다.** 세션마다 스냅숏이 한 개 이상 찍히고, **스냅숏 수가
파일을 바꾼 호출 수와 ±10% 안에서 맞는다.**
*빗나가면*: 다른 것을 보기 전에 배선부터 고친다. 이 예측이 빗나가면 나머지
결과는 읽지 않는다.

**예측 5 — 함정이 적어도 하나는 유발된다.** 여섯 세션을 통틀어 **`빠진 채
종료`나 `회복`이 최소 한 번** 나온다.
*빗나가면*: 발생률이 낮다는 증거는 못 되지만(6개로는 못 잰다) **경고
신호**다. 유저와 함정 설계를 다시 본다.

**미리 적어 두는 교란**: 여섯 세션은 전부 **빈 상태에서 시작**한다. 사슬의
둘째 세션부터 생기는 "물려받은 거짓 기록"은 여기서 관측되지 않는다.

## 5. 문턱을 정하는 규칙 (지금 확정한다)

결과를 보고 고르면 숫자 사냥이다. **도출 규칙을 먼저 못 박는다.**

| 문턱 | 규칙 | 하한 |
|---|---|---|
| 진전 없는 연속 호출 | 여섯 세션에서 관측된 **연속 길이 분포의 90번째 백분위수**를 올림 | 3 |
| 쏠림 창 | **릴리스 항목 하나에 쓴 호출 수의 중앙값** | 10 |
| 쏠림 비율 | 그 창 크기에서 관측된 **한 영역 집중도의 90번째 백분위수** | 0.5 |
| 흔들림 방지 | 한 호출짜리 깜빡임을 90% 이상 없애는 **가장 작은 값** | 3 |

전부 "상위 10%를 이상으로 본다"는 같은 원칙이고, 하한은 지금 코드에 있는
값이다. 규칙이 하한보다 낮은 값을 내면 하한을 쓴다.

## 6. 이 프로브가 답하지 못하는 것

정직하게 적어 둔다. 나중에 결과를 손댈 자리를 많이 읽지 않기 위해서다.

- **함정 발생률.** 6세션으로는 못 잰다. 사전 예측 6("과정 함정 하나가 10%
  이상에서 켜진다")은 프로브가 아니라 **보정의 몫**이다.
- **세션 간 변동.** 6세션은 변동을 논할 표본이 아니다.
- **인수인계.** 단발이라 물려받는 상태가 없다.
- **친숙도.** 대조군이 없다.

## 7. 잠금 절차

1. 유저 승인을 STATUS 결정 로그에 기록한다.
2. `harness/gates.json`의 `collection.state`를 `open`으로 바꾸고, `scope`에
   **"release-traps 손댈 자리의 수를 정하는 프로브, 단발 6세션"**을 적는다. 같은 커밋에서.
3. 돌린다. 중간에 범위를 손댈 자리를 늘리지 않는다.
4. 끝나면 **즉시 다시 잠근다.** 결과를 보기 전에 잠근다 — 결과가 좋으면 더
   돌리고 싶어지는 것을 막기 위해서다.
5. `results/probe/release-traps`를 STATUS의 수집 배치 목록에 한 줄 넣는다
   (`harness/check_records.py`가 이 표를 본다).
6. 예측 다섯 개를 하나씩 대조해 `docs/PROBE_RESULTS.md`에 적는다. **빗나간
   것을 먼저 적는다.**
