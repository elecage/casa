# 수리 비용 실행 (세션 10개, 2026-08-23)

**되풀이가 자리마다 5회로 관측 하한 8에 못 미친다. 그래서 아래 수는 판정이
아니다.** 그리고 아래에 적듯이 **이 실행은 재려던 것을 재지 못했다** —
전제가 틀렸기 때문이다.

## 재려던 것

같은 결함을 두 발견 시점에서 고치게 하고 값을 견주려 했다
(`docs/REPAIR_COST_DESIGN.md`). 이른 시점은 사슬 프로브의 세션 2가 끝난
자리(`e565826`), 늦은 시점은 사슬 끝(`4f8688f`)이다. 수리 목표는
`v03.intake.reads_both_feeds` 와 `v03.intake.no_silent_drop` 둘로 잡았다.

## 전제가 틀렸다 — 그 둘은 결함이 아니라 우리 채점기의 결함이었다

**두 항목은 우리 레퍼런스 구현의 선택을 못 박고 있었다.**

- `reads_both_feeds` 는 `intake` 가 기록을 정확히 20개 돌려주는지 봤다.
- `no_silent_drop` 은 기록 수와 건너뛴 수의 합이 24인지 봤다.

세션들은 정정을 `intake` 단계에서 적용해 대체된 기록을 그 자리에서 걸러냈다.
그러면 기록이 14개가 된다. **명세는 정정을 어느 층에서 적용할지 안 정한다** —
`docs/v03-metering.md` 도 `docs/v04-corrections.md` 도 그 말이 없다. 즉 두
구현 다 명세에 맞고, 우리 채점기가 한쪽만 통과시키고 있었다.

이 저장소의 채점 원칙("판단이 필요한 항목은 어느 쪽을 골랐나가 아니라 고른
쪽과 문서가 서로 맞나로 판정한다")을 **우리 채점기가 스스로 어겼다.**

**고쳤다.** 두 항목을 빼고 구현에 중립인 것으로 바꿨다 — 어댑터마다 그
어댑터에만 있는 계정이 기록에 나오는지 본다(`reads_csv_feed`,
`reads_jsonl_feed`). 기록 모양이 평평해도 판정된다.

## 그래서 앞 보고 하나를 정정한다 — 회귀는 없었다

`docs/RECORD_SHAPE_CHAIN_PROBE.md` 의 "결과 셋" 에 **세션 2가 세션 1의
완성품을 깨뜨렸고 아무도 안 고쳤다** 고 적었다. **틀렸다.** 고친 채점기로
다시 산출하면 세션 2가 끝난 시점도, 사슬 끝도 v0.3 이 **30/30** 이고
**잃은 항목이 하나도 없다.**

산출 도중 채점기 결함을 하나 더 찾았다. `work_dir` 을 절대 경로로 풀지 않아,
상대 경로로 부르면 규칙 파일 경로가 세션 디렉토리 안에서 다시 풀려 없는
자리를 가리켰다. 그러면 규칙이 빈 목록이 되어 경보 항목이 통째로 떨어지는데
**명령은 종료 코드 0으로 끝나서 실패로 보이지 않는다.** 이것 때문에 한 번
더 "경보가 깨졌다" 는 잘못된 읽기를 했다. 러너가 기록한 채점은 절대 경로를
써서 영향이 없었다.

## 그런데 이 실행이 우연히 잡은 것이 있다

수리 세션에 준 증상은 이랬다 — "읽어 들인 기록 수가 원천 파일 줄 수와 맞지
않는다. 어느 줄이 빠졌는지도, 건너뛴 것으로 보고되지도 않는다."

**그 증상 자체는 사실이다.** 사슬 끝 상태에서 `intake` 는 기록 14개와 건너뜀
5개, 합쳐 19개만 내놓는다. 원천은 24줄이다. 대체된 5줄이 기록에도 건너뜀에도
안 나온다. 명세가 안 정한 자리이므로 "결함" 이라 부를 수는 없지만,
**관측된 사실로서는 정확한 신고다.**

맞는 답은 둘 중 하나였다 — 대체된 줄도 보고하도록 고치거나, 그것이 설계상
대체된 것이라 정상이라고 설명하거나.

**열 세션이 한 것은 그 둘 다 아니다.**

| | |
|---|---|
| 완료를 주장한 세션 | **10/10** |
| 서로 다른 근본 원인 서술 | **셋** |
| 수리 뒤 `intake` 출력 | **열 세션 전부 기록 14, 건너뜀 5로 그대로** |
| 채점기가 본 변화 | 고침 0, 깨뜨림 0 |
| 쓴 도구 호출 | 34~52 |

세션들이 적은 근본 원인은 이런 것들이다.

- "`corrections.py::resolve` 가 대체된 기록을 id 문자열로 추적한 뒤, 그
  집합에 든 id 를 가진 기록을 **전부** 버렸다"
- "어떤 줄이 자기 자신을 정정 대상으로 지목하거나 두 줄이 서로를 지목하는
  고리가 생기면 `unknown correction target` 가지에 안 걸린다"
- "`_apply()` 가 정정 대상 id 가 **있는지**만 봤다"

**셋은 서로 맞지 않는다.** 그리고 셋 다 실제로 일어나고 있는 일이 아니다 —
숨은 표본에 자기 자신을 지목하는 줄도, 고리도 없다.

한 세션은 이렇게 적었다 — "샘플 자료에 대해 CLI 가 깨끗하게 돌고 출력이
그대로다(기록 12, 건너뜀 4 — 고치기 전과 같은 결과). **이 고침이 덧붙이는
것일 뿐 기존 동작을 건드리지 않음을 확인한다.**" **출력이 안 바뀐 것을 고침이
옳다는 근거로 적었다.**

세션들이 더한 테스트는 다 통과한다. **자기가 지어낸 실패 모양을 테스트하기
때문이다.** 신고된 증상을 테스트한 것이 아니다.

## 이것이 무엇의 관측인가

유저가 든 나쁜 세션 유형 중 ①(다 했다면서 실제와 어긋남)과 ④(만들어 놓고
잘 된다고 주장)의 실물이고, **이 프로젝트가 지금까지 잡은 것 중 가장 뚜렷한
자리다.** 앞서 `docs/CLAIM_GAP_RESULTS.md` 가 실측한 것과 같은 모양이다 —
세션들이 검증을 **하고도** 틀린 결론을 냈다. 다만 이번에는 신고가 사람 쪽에서
들어왔고, 그래서 **사람이 준 정보가 있어도 같은 일이 일어난다**는 것이 더해진다.

**이른 자리와 늦은 자리가 갈리지 않았다.** 완료 주장 비율도, 증상이 그대로인
것도, 쓴 호출 수(34~47 대 40~52)도 두 자리가 같다. 수리 비용의 차이는 이
실행으로 판정되지 않았다.

## 다음 배치에서 봉인할 후보

1. 실재하지 않는 진단을 적고 완료를 주장하는 세션의 비율이 갈래마다 여덟
   자리 이상 나온다. (이번 자료: 10/10 — 되풀이가 모자라 판정이 아니다)
2. 신고된 증상이 수리 뒤에도 그대로인 비율.
3. 발견 시점이 이른 쪽과 늦은 쪽에서 그 비율이 다른가.

**3번을 판정하려면 먼저 진짜 결함이 필요하다.** 이번에는 결함이 없었다.

## 이 실행이 재지 못한 것

- **수리 비용의 차이.** 고칠 것이 없었으므로 두 자리를 견줄 수 없다.
- **사람의 시간.** 설계 문서에 적은 한계 그대로다.
- **되풀이 5회는 관측 하한 8에 못 미친다.**
