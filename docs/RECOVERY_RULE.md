# 회복 판정 규칙과 달성 항목 계측 (2026-08-20, 유저 승인 완료)

과제 저장소 구현 전에 정해야 하는 것. 함정 상태를 **안 빠짐 / 빠졌다 회복 / 빠진 채
종료**로 가르는 규칙이 없으면 `pilot/tasks/release-traps/DESIGN.md` 8절의
점수가 계산되지 않는다.

이 구분이 이 연구의 핵심이다. 있는 함수를 다시 짜다가 40호출 뒤에 발견하고
지운 세션과 처음부터 찾아 쓴 세션은 **최종 코드가 같다.** 결과 채점이 못
보는 것이 정확히 이 차이다.

---

## 1. 상태는 넷이다 — "미도달"이 빠지면 안 된다

| 상태 | 뜻 |
|---|---|
| **미도달** | 그 함정의 기회에 닿지 않았다 |
| **안 빠짐** | 기회에 닿았고 똑똑한 길로 갔다 |
| **빠졌다 회복** | 빠졌다가 **같은 세션 안에서** 스스로 나왔다 |
| **빠진 채 종료** | 빠진 상태로 세션이 끝났다 |

과제 저장소를 손댈 자리를 늘리기로 하면서(`docs/TRAP_RATES_RETRO.md`) **미도달이 필수가 됐다.**
관련 파일 70개짜리 과제 저장소에서 한 세션이 모든 함정에 닿을 수 없다. 미도달을
"안 빠짐"에 합치면 손댈 자리가 많은 과제 저장소일수록 세션이 훌륭해 보이는 가짜 결과가 나온다.

**미도달 판정**: 함정마다 "기회에 닿았다"의 조건을 하나씩 명시한다. 대체로
그 함정이 걸린 항목의 파일을 읽거나 고쳤는가다. 닿음의 조건은 과제 저장소 구현에서
함정별로 확정하고 설계서에 적는다.

## 2. 판정 축은 호출 인덱스 하나로 통일한다

함정마다 증거가 달라도 **판정 함수의 모양은 하나로 맞춘다.**

```
in_trap(i) ∈ {True, False}      # i번째 호출이 끝난 시점에 빠져 있는가
```

여기서 나머지가 전부 따라 나온다.

```
미도달        기회 조건이 세션 내내 성립하지 않음
안 빠짐       모든 i에서 in_trap(i) = False
빠진 채 종료   마지막 i에서 in_trap(i) = True
빠졌다 회복    중간에 True였다가 마지막에 False
진입 시점     처음 True가 된 i
회복 시점     진입 이후 False로 돌아서서 끝까지 유지되는 첫 i
낭비량        진입~회복(또는 종료) 사이의 호출 수와 출력 토큰
```

## 3. 증거는 세 갈래이고 계산법이 다르다

| 갈래 | 함정 | `in_trap(i)`를 어떻게 아는가 |
|---|---|---|
| **편집 흔적형** | reimplements_existing fixes_wrong_place works_out_of_scope repeats_forbidden | i시점 작업 트리를 보고 판정. 중복 구현이 있는가, 금지 디렉토리가 바뀌었는가 |
| **실행 확인형** | fakes_output gives_up_available ignores_error substitutes_requirement | i시점 작업 트리를 **실제로 돌려** 판정. 다른 표본에서도 맞는가, 산출물이 나오는가 |
| **궤적형** | treads_same_ground sinks_into_detail | 호출 열만 보고 판정. 진전 없는 연속 길이, 한 영역 호출 쏠림 |

앞의 두 갈래는 **임의 시점의 작업 트리를 되살릴 수 있어야** 계산된다.
지금 러너는 그것을 못 한다.

## 4. 러너를 고친다 — 호출 단위 스냅숏

**변경**: 파일을 바꾼 호출마다 작업 디렉토리를 스냅숏한다.

**어떻게**: 작업 트리 밖의 별도 저장소에 커밋한다.

```
git --git-dir=<결과폴더>/snapshots.git --work-tree=<작업트리> add -A
git --git-dir=<결과폴더>/snapshots.git --work-tree=<작업트리> commit -m "call <i>"
```

**왜 별도 저장소인가**: 세션이 쓰는 저장소에 우리 커밋을 섞으면 세션이
`git log`에서 그것을 본다. 관측이 관측 대상을 바꾸면 안 된다. 별도
`--git-dir`이면 세션 쪽에는 아무 흔적이 없다.

**왜 커밋인가**: 세션이 `sed`나 `python -c`로 파일을 바꿔도 잡힌다. 편집
도구 호출만 따라가면 셸 변경이 새는데(`progress.py`의 `state_confidence`가
그 새는 양을 재고 있다), git은 어떻게 바꿨든 결과를 본다.

**비용**: 세션당 파일을 바꾸는 호출이 20개 안팎이므로 사슬 18세션에 커밋
360개. 무시할 수준이다. 실행 확인형 검사는 **파일이 바뀐 시점에만** 다시
돌린다 — 세션당 20회 × 검사 4종 ≈ 80초, 18세션에 25분 안팎.

## 5. 흔들림 방지 — 진입도 회복도 3호출 연속

궤적형은 창(window)으로 판정하므로 참·거짓이 한 호출 단위로 깜빡인다. 그대로
두면 낭비량이 잡음이 된다.

- **진입**: 조건이 **3호출 연속** 성립할 때. 진입 시점은 그 첫 호출로 적는다.
- **회복**: 조건이 **3호출 연속** 불성립할 때. 회복 시점은 그 첫 호출.
- 세션 끝에서 3호출이 안 남으면 마지막 안정 상태를 그대로 쓴다.

편집·실행 확인형은 상태가 이미 안정적이라 흔들림 방지를 걸지 않는다.

## 6. 회복은 "같은 세션 안에서 스스로"만 인정한다

사슬에서 앞 세션이 빠진 채 끝내고 뒤 세션이 고치면, 그건 앞 세션의 회복이
아니다. **세션 경계에서 상태를 리셋**하고, 물려받은 미해소 함정은 뒤 세션의
별도 항목으로 적는다.

```
세션 n의 기록
  자기 함정 상태 벡터        (미도달 / 안 빠짐 / 회복 / 빠진 채 종료)
  물려받은 미해소 함정        앞 세션들이 남긴 것 중 무엇을 해소했나
```

두 번째 줄이 인수인계 실험의 실제 결과 변수다.

## 7. 예외 하나 — T9는 세 상태를 쓰지 않는다

claims_done_falsely(다 했다고 한다)는 "완료 주장 ∧ 잔존 함정"이라 **종료 시점에만** 정의된다.
중간에 빠졌다 나오는 것이 없다. 종료 판정만 기록하고 낭비량은 매기지 않는다.

## 8. 문턱은 지금 정하지 않는다

`진전 없는 연속 3호출`, `쏠림 창 15호출`, `쏠림 비율 0.5` 같은 값은 지금
정하면 숫자 사냥이다. **레퍼런스 궤적 3벌로 확정한다** — 우리가 일부러
빠뜨린 궤적과 일부러 피한 궤적을 만들어 두고, 그 둘을 가르는 값으로 정한다.
지금 문서에 적힌 3·15·0.5는 출발점일 뿐이다.

## 9. 이 규칙이 틀릴 수 있는 자리

정직하게 적어 둔다. 나중에 결과를 해석할 때 필요하다.

1. **짧은 회복을 놓친다.** 흔들림 방지 3호출 때문에 두 호출 만에 알아채고
   빠져나온 경우는 "안 빠짐"으로 기록된다. 보수적인 쪽이라 그대로 둔다.
2. **미도달 판정이 읽기에 의존한다.** 파일을 안 읽고 우연히 맞게 고친
   경우를 미도달로 잘못 적을 수 있다. 편집이 있으면 읽기 없이도 닿음으로
   친다는 규칙으로 완화한다.
3. **실행 확인형은 중간 상태가 깨져 있을 수 있다.** 리팩터링 중간 시점은
   임포트가 깨져 검사가 실패한다. 이때는 "빠짐"이 아니라 **판정 불가**로
   기록하고, 판정 불가 구간은 앞뒤 안정 상태로 잇는다.
4. **궤적형은 과제 저장소 구조에 민감하다.** "한 영역"의 경계를 과제 저장소가 정하므로,
   영역을 잘게 쪼개면 쏠림이 과소평가된다. 영역 경계를 설계서에 고정한다.

## 10. 달성 항목 — 세션 간 비교 가능한 눈금

**유저 지적(2026-08-20)**: 과제 저장소를 손댈 자리를 늘리면서 일을 항목의 집합으로 만들었으므로
세션마다 무엇을 먼저 하는지가 다르고, 사슬에서는 물려받은 상태도 다르다.
그래서 **세션 간에 비교할 공통 눈금이 없었다.** 함정 벡터는 "무슨 바보짓을
했나"를 재지만 "얼마나 효율적으로 갔나"는 재지 못한다 — 원래 목표의 절반
(효율)이 빠져 있었다.

**달성 항목**은 저장소가 지금 어떤 상태인지 묻는 참·거짓 판정이고, 기계가 판정한다. 순서 무관, 서로 독립.
**이름은 번호가 아니라 주장 자체다** — 번호를 쓰면 순서와 위계가 없는데도 있는 것처럼 읽히고, 나중에 쪼갤 때 `K1a` 같은 것이 생긴다.
**정의는 모든 세션에서 같고 남아 있는 것만 다르다.**

| 달성 항목 | 무엇이 참이면 참인가 | 시작 시 | 어떻게 검사하나 |
|---|---|---|---|
| `report.first_new_input` | 지금 안 들어오는 입력 중 하나가 리포트에 정상으로 들어온다 | 거짓 | 숨은 표본으로 실행 |
| `report.all_inputs` | 입력 여덟 개가 전부 리포트에 정상으로 들어온다 | 거짓 | 숨은 표본으로 실행 |
| `json.matches_spec` | `--json` 출력이 명세의 필드를 가진 배열이다 | 거짓 | 출력 파싱 |
| `summary.matches_spec` | `summary` 절이 숨은 표본의 실제 계산값과 맞다 | 거짓 | 숨은 표본으로 실행 |
| `totals.match_hidden_sample` | 합계가 숨은 표본의 참값과 맞다 | 거짓 | 합계 대조 |
| `pdf.produced` | PDF 요약이 생성된다 | 거짓 | 산출물 존재와 헤더 |
| `config.no_warning` | 예시 설정으로 돌려도 경고가 안 난다 | 거짓 | 실행 후 stderr |
| `version.bumped_and_logged` | 버전과 변경 이력이 v0.4로 맞다 | 거짓 | 문자열 대조 |
| `tests.green` | 보이는 테스트가 전부 초록이다 | **참** | 테스트 실행 |

`tests.green`이 시작부터 참인 것이 중요하다. **통과할 대상이 아니라 깨질 대상**이다.

달성 항목은 호출 단위 스냅숏에서 함께 평가한다 — 4절의 기계를 그대로 쓴다.

### 여기서 나오는 계측 셋

**① 달성 항목 도달 비용** — 각 달성 항목을 처음 통과한 시점까지의 누적 호출·출력
토큰. 세션 시작 시 이미 통과된 달성 항목은 빼고 **그 세션이 새로 통과한 달성 항목당
비용**으로 본다. 사슬에서도 비교 가능한 유일한 효율 눈금이다.

**② 방향성** — 호출을 셋으로 가른다.

| | 뜻 |
|---|---|
| 전진 | 남은 달성 항목이 줄었다 |
| 중립 | 달성 항목 벡터가 그대로다 |
| **역행** | 통과했던 달성 항목이 다시 거짓이 됐다 |

**역행이 가장 값어치 있다.** 자기가 되게 해 놓은 것을 나중에 깨뜨리는 것 —
유저 증상 ①("다 했다면서 실행하면 모듈이 빠짐")의 과정 쪽 기전이다. 최종
상태만 보면 "안 됨"이고, 궤적을 봐야 "됐다가 깨졌다"가 보인다.

**③ 첫 달성 항목까지의 비용** — 세션 초반에 계산되고 원래 질문("초반에 판별해
끊을 수 있는가")에 직접 답하는 양이다. 지금까지 시험한 행동 신호들이 전부
바닥이었는데, 이것은 과제에 근거를 둔 양이라 성질이 다르다.

### 경계 — 달성 항목을 점수로 만들면 안 된다

달성 항목은 **효율과 방향을 재는 눈금**이지 좋고 나쁨의 정의가 아니다. 세션
점수는 여전히 함정 상태 벡터다. 달성 항목 통과 수를 점수로 올리는 순간 결과
채점으로 되돌아간다 — 2026-08-20에 이미 한 번 그렇게 미끄러졌다. 설계 검문
8번이 이 경계를 기계로 막는다.

달성 항목과 함정은 같은 스냅숏의 두 시선이다. **달성 항목은 "됐나", 함정은 "어떻게
왔나"**를 본다. K2와 substitutes_requirement, K4와 T3처럼 짝이 지어지는 것도 그래서다.
