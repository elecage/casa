# 다세션 프로젝트 arm — 설계 제안 (2026-08-19)

유저 지적 세 가지에서 출발한다.

1. 끊어서 이득이 되는 최소 크기를 제안할 수 있는가 → **가능하다**
   (`docs/RESTART_EVAL_RESULTS.md` 4절: 알림이 30% 지점에 뜬다는 조건에서
   세션당 약 29,000 출력 토큰).
2. 그러면 큰 프로젝트로 실험해야 한다.
3. **그런데 큰 프로젝트는 여러 세션으로 쪼개진다. 그 분할 자체의 영향이
   있고, 세션 간 능력 차이는 원래 그렇게 쪼갤 때 두드러진다.**

세 번째가 이 문서의 핵심이다.

---

## 1. 지금 설계가 현상을 담지 못한다

원래 목표는 **"같은 프로젝트에서 새 세션을 열 때마다 능력이 다르다"**이다.
`새 세션을 열 때마다`라는 말이 이미 **여러 세션에 걸친 프로젝트**를 전제한다.

그런데 지금 실험은 **과제 하나 = 세션 하나**다. 세션이 하나뿐인 설계에서는
세션 간 차이를 관측할 수 없다. 우리는 세션 *안*의 병리를 재고 있었고, 유저가
겪는 현상은 세션 *사이*에서 벌어진다.

이것은 2026-08-19에 이미 지적된 구성 타당도 문제(`docs/W15_ABILITY_EARLY.md`
1절)와 **같은 종류의 문제이고, 아직 남아 있는 부분**이다.

## 2. 실측이 이 방향을 가리킨다

`docs/RESTART_EVAL_RESULTS.md`에서 나온 숫자 하나가 결정적이다.

> **문맥 재확보 비용 H = 5,853 토큰 = 세션 총 비용의 72%**

세션 비용의 대부분이 "읽고 파악하기"다. 그리고 **세션을 나누면 그 비용을
경계마다 다시 낸다.** 즉 분할의 비용은 추상적 우려가 아니라 이미 측정된
양이고, 그 크기가 세션의 3분의 2다.

동시에 이것이 기회다. **H는 인수인계 품질에 따라 달라진다.** 앞 세션이 무엇을
남겼는지에 따라 다음 세션이 자리 잡는 속도가 달라지고, 그 차이가 곧 토큰이다.

## 3. 그래서 H를 상수가 아니라 결과변수로 만든다

이것이 이 설계의 중심 아이디어다.

| 지금 | 바뀌는 것 |
|---|---|
| H는 손익분기 계산의 입력 상수 | **H는 세션마다 측정되는 결과변수** |
| 인수인계는 실험 밖 | **인수인계 품질이 관측 대상** |
| 세션 간 차이 관측 불가 | **세션 간 차이가 곧 H와 진척의 분산** |

**세션 간 능력 차이가 가장 잘 드러나는 지점이 인수인계이고, `H`가 그것의
정량 측정이다.** 앞 세션이 남긴 상태를 잘 집어 드는 세션과 그러지 못하는
세션이 갈리는 곳이 여기다.

이 프로젝트 자체가 사례를 갖고 있다. `STATUS.md`가 존재하는 이유가 정확히
이것이고, 그럼에도 한 세션이 수집 배치 7개를 기록하지 않아 3주 뒤에야 다른
세션이 우연히 발견했다.

## 4. 설계

### 4.1 형태

하나의 저장소에서 **연속된 세션 사슬**로 프로젝트를 진행한다.

- 세션 i는 세션 i−1이 남긴 저장소 상태 + 인수인계 기록에서 시작한다.
- 세션 경계는 **고정 예산**으로 강제한다(호출 수 또는 출력 토큰 상한).
  에이전트가 스스로 멈추게 두면 분할 지점이 내생 변수가 되어 비교가 깨진다.
  고정 예산은 실제 사용 한도와도 닮았다.
- 사슬 하나가 관측 단위이고, 같은 프로젝트를 여러 사슬로 반복한다.

### 4.2 무엇을 재는가

세션마다:

| 측정 | 뜻 |
|---|---|
| **H_i** 첫 수정 전 소비 토큰 | 자리 잡는 데 든 비용 = 인수인계를 얼마나 잘 받았나 |
| **진척_i** 그 세션이 완료한 검사 가능한 항목 수 | 실제로 나아간 양 |
| **비용_i** 출력 토큰 | |
| 경보 상태 | 세션 안의 병리 |
| **인수인계 산출물** | 다음 세션에 무엇을 남겼는가 (기록 갱신 여부·정확도) |

사슬마다: 총 비용, 완료 여부, **세션 간 진척의 분산**.

### 4.3 끊기 결정이 달라진다

연속 프로젝트에서는 **끊어도 커밋된 상태가 남는다.** 그래서 재시작 비용이
단발 과제보다 훨씬 싸고, 손익분기가 실제로 도달 가능해진다. 지금까지의
"재시작은 손해" 결론은 **단발 설계의 산물**일 가능성이 크다.

이것이 이 arm이 답할 수 있는 새 질문이다.

## 5. 분할이 만드는 교란과 그 처리

유저가 짚은 대로 분할 자체가 결과에 영향을 준다. 무시하지 않고 설계에 넣는다.

| 교란 | 처리 |
|---|---|
| 분할 지점이 결과를 좌우한다 | 고정 예산으로 외생화. 예산 크기를 조건으로 두어 그 효과 자체를 측정 |
| 인수인계 품질이 다음 세션을 좌우한다 | **통제하지 않는다 — 이것이 측정 대상이다.** 다만 인수인계 형식(있음/없음/구조화)을 조건으로 나눔 |
| 앞 세션의 실패가 뒤 세션에 누적된다 | 사슬 단위 분석. 세션을 독립 표본으로 취급하지 않는다 |
| 사슬끼리 서로 오염 | 사슬마다 별개 저장소·별개 트랜스크립트 디렉토리 (기존 러너 격리 방식 그대로) |

**주의**: 지금까지 방법론 방어로 써온 "세션 독립성"은 **사슬 안에서는
성립하지 않는다.** 사슬 내 세션은 의도적으로 의존적이다. 사슬 *사이*의
독립성만 주장할 수 있고, 분석 단위를 사슬로 올려야 한다. 기존 결론을 이
arm에 그대로 옮기면 안 된다.

## 6. 이 arm이 미해결 설계 문제도 함께 푼다

`harness/TASK_DESIGN_RUBRIC.md`의 일곱 항목은 단발 과제가 만족하지 못했다.
연속 프로젝트는 구조상 대부분을 만족한다.

| 루브릭 | 다세션 프로젝트에서 |
|---|---|
| 판단 단계 | 앞 세션이 남긴 것 중 무엇이 맞는지 판정해야 한다 |
| 상충 요구 | 기록과 코드가 어긋나 있을 수 있다 |
| **기존 상태와의 정합** | **구조 자체가 이것이다** |
| 애매함 | 인수인계는 늘 불완전하다 |
| **길이와 규율** | **길다. 규율이 무너질 시간이 있다** |
| 채점 환원 | 사슬의 최종 산출물을 결정론적으로 검사 |
| 기술적 실패 분리 | 세션 단위로 분리 집계 |

즉 **이 arm은 크기 문제와 과제 설계 문제를 동시에 겨냥한다.**

## 7. 확정된 설계 (2026-08-19, 유저 결정)

### 7.1 채점 — 마일스톤 오라클

프로젝트를 **서로 독립인 마일스톤 M개**로 쪼개고 각각에 숨은 검사를 붙인다.
사슬의 점수는 끝났을 때 통과한 마일스톤 수(0~M)다.

이 방식이 셋을 한꺼번에 푼다.

| | |
|---|---|
| **결정론 채점** | 마일스톤마다 통과/실패가 기계 판정. 심판 불요 |
| **결과에 변동이 생김** | 이진값이 아니라 0~M. "잴 변동이 없다"는 그간의 벽이 풀린다 |
| **세션별 진척이 공짜** | 세션 i 동안 실패→통과로 뒤집힌 개수. 러너가 세션 경계마다 채점하되 **에이전트에게는 알리지 않는다** |

설계 제약:
- 마일스톤은 **서로 독립**이어야 한다. 앞의 것이 막히면 뒤가 전부 막히는
  구조면 부분 점수가 의미를 잃는다.
- 검사는 **숨긴다**. 보이면 그것만 겨냥한다(단발 과제에서 이미 겪은 포화).
- 마일스톤 수 **8~10**. 사슬 길이보다 많아야 매 세션 할 일이 남는다.

### 7.2 인수인계 품질 측정 — 재발견 비율

8절에서 미해결이던 항목의 답이다. H를 대리 지표로 쓰면 인수인계 품질 외의
요인(진짜 작업 범위 파악)이 섞인다. 주 지표를 바꾼다.

> **재발견 비율 = 세션 i+1이 읽은 것 중 세션 i가 이미 읽었던 것의 비율**

인수인계가 좋으면 다음 세션이 같은 파일을 다시 뒤질 필요가 없다. **인수인계가
실제로 아낀 것을 직접 잰다.** 트랜스크립트만으로 계산되고, 이미 구현된
재열람 비율(`casa.signals.reread_ratio`)을 사슬 수준으로 올린 것이다.

보조 지표: H(첫 수정 전 소비), 첫 마일스톤 통과까지의 비용, **인수인계
산출물의 존재 여부**.

마지막 것이 중요하다. 인수인계를 "남겨라"고 프롬프트로 시키는 것은 이
프로젝트 원칙상 **강제가 아니라 측정 대상**이다. 그러니 "실제로 남겼는가"가
관측값이 된다. 우리 프로젝트가 산 증거다 — `CLAUDE.md`에 "같은 커밋에서
STATUS를 갱신하라"고 적혀 있었는데 한 세션이 수집 배치 7개를 기록하지 않아
3주 뒤에야 발견됐다.

### 7.3 규모 — 손익분기에서 역산

| 항목 | 값 | 근거 |
|---|---|---|
| 세션당 예산 | **도구 호출 60회** | 30% 지점 알림 기준 손익분기 29,000토큰 ÷ 호출당 약 500토큰 |
| 사슬 길이 | **6세션** | 세션 간 변동을 보려면 최소 4~5 |
| 마일스톤 | **8~10** | 사슬 길이보다 많게 |
| 보정 | **사슬 3개** | 기존 관행(본 수집 전 n=3) |

**예산이 실제로 걸려야 한다.** 일이 20호출에 끝나는데 60을 강제하면 인위적
이다. 프로젝트를 한 세션 예산보다 확실히 크게 잡아 **예산이 진짜 제약**이
되게 한다 — 실제 사용 한도가 그렇게 작동한다.

### 7.4 프로젝트 소재 — 목적 제작 (유저 결정)

새로 만든다. 채점이 확실하고 반복 가능하기 때문이다. 대신 **구조는 실무를
닮게** 한다: 둘째 세션부터는 절반 된 변경·낡은 문서·기록과 코드의 어긋남이
자연히 쌓이므로, 첫 세션에만 인위적 시작 상태를 준다.

현실성이 낮다는 약점은 인정하고 한계 절에 적는다. 실제 레포 교차 검증은
방법이 확립된 뒤로 미룬다.

### 7.5 인수인계 조건 — 보정은 자유형만 (유저 결정)

보정 사슬 3개는 "기록을 남겨라"만 지시하고 형식은 자유로 둔다. **방법 자체가
도는지 먼저 확인**하고, 본 수집에서 없음/자유/구조화 세 조건을 대조한다.

보정에서 방법이 안 돌면 세 조건을 다 돌린 비용이 통째로 버려진다.

## 8. 진행 조건과 남은 것

**새 수집이 필요하므로 수집 잠금 해제가 선행이다** (`harness/gates.json`).
잠금 해제 조건은 "새 과제군의 채점 방법을 먼저 확정하고, 유저 승인을
`STATUS.md` 결정 로그에 기록한 뒤 state를 open으로" 이다. 채점 방법은
7.1에서 확정됐으므로 남은 것은 **유저의 명시적 해제 승인**뿐이다.

### 7절에서 해소된 미해결 항목

| 이전 미해결 | 해소 |
|---|---|
| 사슬 길이를 몇으로 | 6세션 (7.3) |
| 사슬 단위 결정론 채점 | 마일스톤 오라클 (7.1) |
| 인수인계 품질의 결정론 측정 | 재발견 비율 (7.2) |

### 아직 남은 것

1. **마일스톤 8~10개의 구체 명세.** 서로 독립이면서 프로젝트로서 말이 되는
   분할을 실제로 짜야 한다. 이것이 다음 산출물이다.
2. **`pilot/tasks/<name>/DESIGN.md`** — 새 과제이므로
   `harness/check_task_design.py`가 루브릭 7항목을 요구한다. 미작성이면
   커밋이 거부된다. 우리 하네스가 여기서 처음으로 실제 일을 한다.
3. **러너의 세션 사슬 지원.** 지금 `pilot/run_sessions.py`는 독립 세션을
   반복 실행한다. 사슬은 (a) 앞 세션의 작업 디렉토리를 이어받고 (b) 호출
   예산에서 끊고 (c) 세션 경계마다 마일스톤을 채점해야 한다. 셋 다 없다.
4. **규모 산정** — `pilot/analysis/power.py`.
5. **현실성 한계 명시.** 목적 제작이므로 외적 타당도가 낮다. 실제 레포
   교차 검증은 방법 확립 후로 미룬다.
