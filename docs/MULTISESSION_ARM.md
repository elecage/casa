# 다세션 프로젝트 arm — 설계 제안 (2026-08-19)

유저 지적 세 가지에서 출발한다.

1. 끊어서 이득이 되는 최소 크기를 제안할 수 있는가 → **가능하다**
   (`docs/RESTART_EVAL_RESULTS.md` 4절: 알림이 30% 지점에 뜬다는 조건에서
   세션당 약 29,000 출력 토큰).
2. 그러면 큰 프로젝트로 실험해야 한다.
3. **그런데 큰 프로젝트는 여러 세션으로 쪼개진다. 그 분할 자체의 영향이
   있고, 세션 간 능력 차이는 원래 그렇게 쪼갤 때 두드러진다.**

세 번째가 이 문서의 핵심이다.

---

## 1. 지금 설계가 현상을 담지 못한다

원래 목표는 **"같은 프로젝트에서 새 세션을 열 때마다 능력이 다르다"**이다.
`새 세션을 열 때마다`라는 말이 이미 **여러 세션에 걸친 프로젝트**를 전제한다.

그런데 지금 실험은 **과제 하나 = 세션 하나**다. 세션이 하나뿐인 설계에서는
세션 간 차이를 관측할 수 없다. 우리는 세션 *안*의 병리를 재고 있었고, 유저가
겪는 현상은 세션 *사이*에서 벌어진다.

이것은 2026-08-19에 이미 지적된 구성 타당도 문제(`docs/W15_ABILITY_EARLY.md`
1절)와 **같은 종류의 문제이고, 아직 남아 있는 부분**이다.

## 2. 실측이 이 방향을 가리킨다

`docs/RESTART_EVAL_RESULTS.md`에서 나온 숫자 하나가 결정적이다.

> **문맥 재확보 비용 H = 5,853 토큰 = 세션 총 비용의 72%**

세션 비용의 대부분이 "읽고 파악하기"다. 그리고 **세션을 나누면 그 비용을
경계마다 다시 낸다.** 즉 분할의 비용은 추상적 우려가 아니라 이미 측정된
양이고, 그 크기가 세션의 3분의 2다.

동시에 이것이 기회다. **H는 인수인계 품질에 따라 달라진다.** 앞 세션이 무엇을
남겼는지에 따라 다음 세션이 자리 잡는 속도가 달라지고, 그 차이가 곧 토큰이다.

## 3. 그래서 H를 상수가 아니라 결과변수로 만든다

이것이 이 설계의 중심 아이디어다.

| 지금 | 바뀌는 것 |
|---|---|
| H는 손익분기 계산의 입력 상수 | **H는 세션마다 측정되는 결과변수** |
| 인수인계는 실험 밖 | **인수인계 품질이 관측 대상** |
| 세션 간 차이 관측 불가 | **세션 간 차이가 곧 H와 진척의 분산** |

**세션 간 능력 차이가 가장 잘 드러나는 지점이 인수인계이고, `H`가 그것의
정량 측정이다.** 앞 세션이 남긴 상태를 잘 집어 드는 세션과 그러지 못하는
세션이 갈리는 곳이 여기다.

이 프로젝트 자체가 사례를 갖고 있다. `STATUS.md`가 존재하는 이유가 정확히
이것이고, 그럼에도 한 세션이 수집 배치 7개를 기록하지 않아 3주 뒤에야 다른
세션이 우연히 발견했다.

## 4. 설계

### 4.1 형태

하나의 저장소에서 **연속된 세션 사슬**로 프로젝트를 진행한다.

- 세션 i는 세션 i−1이 남긴 저장소 상태 + 인수인계 기록에서 시작한다.
- 세션 경계는 **고정 예산**으로 강제한다(호출 수 또는 출력 토큰 상한).
  에이전트가 스스로 멈추게 두면 분할 지점이 내생 변수가 되어 비교가 깨진다.
  고정 예산은 실제 사용 한도와도 닮았다.
- 사슬 하나가 관측 단위이고, 같은 프로젝트를 여러 사슬로 반복한다.

### 4.2 무엇을 재는가

세션마다:

| 측정 | 뜻 |
|---|---|
| **H_i** 첫 수정 전 소비 토큰 | 자리 잡는 데 든 비용 = 인수인계를 얼마나 잘 받았나 |
| **진척_i** 그 세션이 완료한 검사 가능한 항목 수 | 실제로 나아간 양 |
| **비용_i** 출력 토큰 | |
| 경보 상태 | 세션 안의 병리 |
| **인수인계 산출물** | 다음 세션에 무엇을 남겼는가 (기록 갱신 여부·정확도) |

사슬마다: 총 비용, 완료 여부, **세션 간 진척의 분산**.

### 4.3 끊기 결정이 달라진다

연속 프로젝트에서는 **끊어도 커밋된 상태가 남는다.** 그래서 재시작 비용이
단발 과제보다 훨씬 싸고, 손익분기가 실제로 도달 가능해진다. 지금까지의
"재시작은 손해" 결론은 **단발 설계의 산물**일 가능성이 크다.

이것이 이 arm이 답할 수 있는 새 질문이다.

## 5. 분할이 만드는 교란과 그 처리

유저가 짚은 대로 분할 자체가 결과에 영향을 준다. 무시하지 않고 설계에 넣는다.

| 교란 | 처리 |
|---|---|
| 분할 지점이 결과를 좌우한다 | 고정 예산으로 외생화. 예산 크기를 조건으로 두어 그 효과 자체를 측정 |
| 인수인계 품질이 다음 세션을 좌우한다 | **통제하지 않는다 — 이것이 측정 대상이다.** 다만 인수인계 형식(있음/없음/구조화)을 조건으로 나눔 |
| 앞 세션의 실패가 뒤 세션에 누적된다 | 사슬 단위 분석. 세션을 독립 표본으로 취급하지 않는다 |
| 사슬끼리 서로 오염 | 사슬마다 별개 저장소·별개 트랜스크립트 디렉토리 (기존 러너 격리 방식 그대로) |

**주의**: 지금까지 방법론 방어로 써온 "세션 독립성"은 **사슬 안에서는
성립하지 않는다.** 사슬 내 세션은 의도적으로 의존적이다. 사슬 *사이*의
독립성만 주장할 수 있고, 분석 단위를 사슬로 올려야 한다. 기존 결론을 이
arm에 그대로 옮기면 안 된다.

## 6. 이 arm이 미해결 설계 문제도 함께 푼다

`harness/TASK_DESIGN_RUBRIC.md`의 일곱 항목은 단발 과제가 만족하지 못했다.
연속 프로젝트는 구조상 대부분을 만족한다.

| 루브릭 | 다세션 프로젝트에서 |
|---|---|
| 판단 단계 | 앞 세션이 남긴 것 중 무엇이 맞는지 판정해야 한다 |
| 상충 요구 | 기록과 코드가 어긋나 있을 수 있다 |
| **기존 상태와의 정합** | **구조 자체가 이것이다** |
| 애매함 | 인수인계는 늘 불완전하다 |
| **길이와 규율** | **길다. 규율이 무너질 시간이 있다** |
| 채점 환원 | 사슬의 최종 산출물을 결정론적으로 검사 |
| 기술적 실패 분리 | 세션 단위로 분리 집계 |

즉 **이 arm은 크기 문제와 과제 설계 문제를 동시에 겨냥한다.**

## 7. 진행 조건

- **새 수집이 필요하므로 수집 잠금 해제가 선행**이다
  (`harness/gates.json`, 유저 승인 사항).
- 잠금 해제 전에 정할 것: 프로젝트 소재, 세션당 예산, 사슬 길이, 사슬 수,
  결정론적 최종 채점 방식, 인수인계 형식 조건.
- 규모 산정은 `pilot/analysis/power.py`.

## 8. 미해결

- **사슬 길이를 몇으로 할 것인가.** 손익분기 계산은 세션당 29,000 토큰을
  가리키지만, 사슬 길이는 별개 결정이다.
- **최종 채점을 사슬 단위로 어떻게 결정론화할 것인가.** 단발 과제의 숨은
  오라클 방식이 그대로 옮겨가지 않는다.
- **인수인계 품질을 어떻게 결정론적으로 재는가.** 지금 안은 H를 대리
  지표로 쓰는 것인데, H는 인수인계 품질 외의 요인도 섞는다.
