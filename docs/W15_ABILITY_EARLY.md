# W15 — 능력 축 조기 탐지 실측, 그리고 미해결로 남은 설계 문제 (2026-08-19)

이 문서는 두 가지를 남긴다.

1. 기존 127세션에 **능력 축 조기 탐지**를 처음 계산한 결과 (신규 수집 0).
2. 그 계산이 **해결하지 못한 문제** — 유저가 제기한 실험 설계의 구성
   타당도 문제. **이 문제는 이 세션에서 해결되지 않았고, 다음 세션의
   출발점이다.**

두 번째가 더 중요하다. 순서를 그렇게 읽어야 한다.

---

## 1. 미해결 문제 (다음 세션이 여기서 시작한다)

### 문제의 형태

유저 지적(2026-08-19): **재는 대상이 잘못 정의돼 있다.** 기록된 목표
(`memory/casa-research-focus.md`)는 "같은 프로젝트에서 새 세션을 열 때마다
업무 처리 능력이 다르다 → 초반에 판별해 끊고 재시작하면 토큰·시간을
아낀다"이고, 능력은 통과/실패가 아니라 효율과 주장-실제 간극으로 정의됐다.

그런데 과제 열 개(`pilot/tasks/`)를 전부 읽어보면 구조가 하나다:

> "이 저장소에 함수 하나가 비어 있다(또는 테스트가 깨져 있다). 명세는
> 문서에 다 적혀 있다. 테스트를 통과시키고 커밋하라."

목표가 하나, 명세가 완전, 산출물이 하나, 판정이 이진. 여기에는 **무엇이
문제인지 판단하는 단계, 상충하는 요구 사이의 선택, 기존 상태(앞선 작업
기록·낡은 문서·절반 된 변경)와의 정합, 애매함에 대한 처리, 규율이 무너질
만한 길이**가 전부 빠져 있다. 유저가 실무에서 능력 차이로 체감하는 것은
거의 전부 그 빠진 목록에 있다.

### 이 세션이 한 일과 하지 못한 일

- **한 일**: 기존 과제 집합 안에서 표적을 능력 축으로 바꿔 계산했다(아래 2절).
- **하지 못한 일**: **설계를 고치지 않았다.** 새 과제군을 만들지 않았고,
  결과 변수도 여전히 기존 채점기의 산출물이다.

아래 2절의 수치는 **유저 비판의 반박이 아니라 근거**다. "기존 과제 집합에서
쥐어낼 수 있는 최대치가 이 정도"라는 상한을 보여주는 것이지, 목표가 달성
불가능하다는 증명이 아니다. 두 문장을 혼동하면 안 된다.

- (A) "이 과제 집합에서는 능력 축 조기 탐지가 이익을 내지 못한다" — 실측됨.
- (B) "세션 능력의 조기 탐지는 불가능하다" — **검정된 적 없음.** 능력 차이가
  드러나는 과제군이 아직 존재하지 않으므로 검정할 수단이 없다.

이전 세션들이 (A)를 (B)로 일반화하면서 방향이 어긋났다. 되풀이하지 말 것.

### 반복되는 오류 패턴 (기록해 두는 이유)

같은 오류가 이 프로젝트에서 세 번 나타났다.

1. 궤도 과제 60세션 완주 후 "단일 파일 수치 퍼즐이라 유저의 실제 실패 경험과
   맞지 않는다"고 판정하고 방향을 틀었으나, 대체로 만든 과제도 결국 "함수
   하나 구현"이었다(2026-07-25).
2. 통과/실패에 분산이 없자 성공률 40~80% 구간을 사냥했다 — 유저가 명시적으로
   금지한 것([[dont-fixate-on-success-rate]]).
3. 2026-08-19 이 세션: 유저가 설계 문제를 제기했는데 **세 번 연속 기존 설계의
   측정 결과로 답했다.** 과제군 재설계 제안 → 능력 축 재계산 → 결과의 범위
   한정. 전부 측정 이야기였고 설계 이야기가 아니었다.

근본 원인은 진단돼 있다: **"결정론적으로, 값싸게, 사람 개입 없이 채점 가능"
이라는 제약이 과제 설계를 매번 "산출물 하나를 임계값 하나로 재기"로
끌어당긴다.** 그러면 판단·정합·규율 차원이 설계에서 탈락한다. 다음 세션은
이 제약을 우회하는 채점 방법부터 정해야 한다(아래 4절).

### 이 세션 자체가 남긴 증거

유저 지적: 이 세션의 진행 자체가 연구의 필요성과 실패를 동시에 보여준다.
관찰된 사실만 적는다.

- 이 세션은 방향을 세 번 잘못 잡아 유저가 세 번 교정했다(설계 문제 → 측정
  답변, 표준 용어와 내부 조어를 섞어 쓴 것, 목표 재확인 요구).
- 앞선 세션이 수집한 7세션(`results/main2/ml-shift-sonnet`)이 상태 기록
  파일에 기재되지 않은 채 남아 있었다. 이 세션은 그것을 발견했으나, 발견
  여부 자체가 세션마다 갈릴 수 있는 종류의 일이다.
- 수집된 데이터 안에도 같은 종류의 사건이 있다: 한 세션이 도구 호출 248회,
  동일 호출 38회 반복, 86분 후 시간 초과로 강제 종료, 규칙 위반 58건(같은
  조건의 다른 6세션은 위반 0).

이것들은 **발견이 아니라 동기**다. 통제되지 않은 관찰이므로 결과로 쓸 수
없다. 다만 "재려는 대상이 실재한다"는 근거로는 충분하고, 현재 과제 집합이
그 대상을 담지 못한다는 점을 뒷받침한다.

## 2. 실측 결과 (기존 127세션, 신규 수집 0)

재현:

```
.venv/Scripts/python.exe pilot/analysis/ability_early.py results/main2/* --tasks-root pilot/tasks
```

### 왜 이 계산이 그때까지 없었나

`docs/RESEARCH_PLAN.md`는 2026-07-24 개정에서 예측 대상에 "성공하지만
고비용인 세션"과 "허위 완료 위험이 있는 세션"을 이미 추가해 두었다. 계획서는
옳았다. 그러나 2차 수집 이후 실제로 계산된 조기 예측은 전부 통과/실패
표적이었고(`pilot/analysis/signal_validation.py`에는 초반 k스텝 로직이 아예
없다 — 세션 종료 후 지표만 사용), 능력 축은 한 번도 계산되지 않았다.

### 표적과 예측자

- 표적 셋: **고비용**(조건 내 최종 출력 토큰 상위 4분위), **허위 완료**(완료를
  주장하고 숨은 채점에 실패), **성공 세션 내 고비용**.
- 예측자: 첫 k번째 도구 호출까지만 보이는 신호 10종(누적 출력 토큰, 탐색
  횟수, 읽은 파일 수, 관련 파일 커버리지, 오류, 동일 호출 반복, 테스트 실행,
  자체 검증, 규칙 위반, 편집 시작 여부). k = 2, 4, 8, 16.
- 벽시계 시간 미사용(서빙 부하 교란, 2026-07-24 결정).
- 조건별로만 보고 — 조건을 섞는 것이 앞선 분석에서 신호를 죽였다.

### (1) 능력 축에 변동은 실재한다

한 조건(같은 과제·같은 모델) 안에서 최종 출력 토큰:

| 조건 | 최소 | 중앙값 | 최대 | 도구 호출 중앙값 |
|---|---|---|---|---|
| 궤도 전파 / 상위 모델 (n=60) | 27 | 12,532 | 60,527 | 16 |
| 계층형 원장 / 하위 모델 (n=30) | 84 | 7,190 | 13,213 | 19.5 |
| 일정 계획 / 하위 모델 (n=30) | 2,858 | 5,536 | 10,669 | 13 |

### (2) 초반에 정보를 가진 신호는 하나뿐

판별력(0.5 = 동전 던지기, 1.0 = 완벽):

- **누적 출력 토큰**: 스텝 2에서 0.50~0.69, 스텝 8에서 0.78~0.88.
- **나머지 9종 전부 0.4~0.6** — 세 조건 모두에서 무신호.

허위 완료 예측도 약하고 조건마다 다른 신호가 뜬다(최대는 일정 조건의 오류
누적 0.79, 단 30세션 중 26이 양성이라 음성 표본 4개로 불안정).

### (3) 재시작 규칙은 대체로 손해

성공 하나당 토큰. **귀무 정책(신호를 전혀 쓰지 않고 스텝 k에서 전부 죽이기)**
을 함께 계산한 것이 핵심이다 — 성공률이 낮은 조건에서는 조기 중단 후
재추첨만으로도 산술적으로 개선되므로, 귀무를 못 이기면 판별력을 입증한 게
아니다.

| 조건 | 아무것도 안 함 | 전부 죽이기 | 최적 탐지기 | 부작용 |
|---|---|---|---|---|
| 일정 / 하위 (성공 1/30) | 179,521 | 173,945 | **132,611 (+26%)** | 12죽임, 성공 0 |
| 궤도 / 상위 (성공 5/60) | 219,327 | 324,784 | 215,822 (+1.6%) | 7죽임, 성공 0 |
| 원장 / 하위 (성공 26/30) | 8,235 | 8,688 | 7,827 (+5%) | 4죽임, **그중 3이 성공** |

성공률이 높으면 죽이는 순간 성공을 죽이고, 성공률이 바닥이면 교체 세션도
실패한다. 유일한 +26%도 이점의 전부가 "그 조건의 유일한 성공 세션 하나가
우연히 임계값 밑에 있었다"에 걸려 있다.

### (4) 회수 가능한 잔액 자체가 적다 (정확도와 무관한 상한)

스텝 8 이후에 태워지는 토큰 비중:

| 조건 | 실패할 세션 몫 (완벽한 탐지기의 최대 회수) | 성공할 세션 몫 (멈추면 파괴) |
|---|---|---|
| 원장 / 하위 | 9% | 61% |
| 궤도 / 상위 | 13% | 10% |
| 일정 / 하위 | 31% | 1% |
| 표 분류 / 상위 (n=7) | 54% | 29% |

소비가 앞쪽에 몰려 있다. 궤도 1번 세션은 두 번째 도구 호출 시점에 이미 전체의
78%를 태웠다(코드를 한 번에 써내는 응답 하나가 12,148 토큰).

### (5) 범위 한정 — 이 수치가 말하지 않는 것

- **프롬프트를 고쳐서 재시작하는 경우는 계산하지 않았다.** 시뮬레이션은
  "같은 조건에서 새로 뽑기"만 다뤘다. 실무의 재시작은 보통 지시를 다듬는
  것이므로 다른 분포에서 뽑는 것이고, 계산이 달라진다. 미검정.
- **세션이 짧다.** 도구 호출 중앙값 13~19회. 스텝 8은 이미 절반이 지난
  시점이라 "조기"라 부를 여유가 거의 없다. 248회 호출 세션 같은 긴 세션은
  이 데이터로 검정되지 않았다.
- **사후 측정은 잘 된다.** 얼마 썼는지, 허위로 완료를 주장했는지, 퇴화했는지는
  기록만으로 명확하다. 실패한 것은 예측이지 측정이 아니다.

### (6) 분석 중 잡은 버그 3건 (전부 결론을 바꿨음, 테스트로 고정)

1. 대화 기록은 어시스턴트 메시지 하나를 **콘텐츠 블록마다 반복 기록**하고 각
   복사본이 같은 토큰 사용량을 들고 있다. 단순 합산은 궤도 1번 세션을 43,131
   토큰으로 부풀렸다(도구 자체 보고는 15,906). 이 오류는 "회수 가능 잔액"을
   3배 과소평가한 수치를 만들었다 → 메시지 식별자로 1회만 계수.
2. 재시작 시뮬레이션에서 스텝 k 전에 끝난 세션을 제외하면 긴 세션만으로
   정책을 평가해 유리하게 왜곡된다 → 전원 포함, 짧은 세션은 표시 불가 처리.
3. 임계값을 2~3개 점에 맞추는 것은 정책이 아니다 → 채점 가능 세션 4개 미만 거부.

`tests/test_ability_early.py` (18개)가 세 건을 회귀 테스트로 고정한다.

## 3. 힌트 제거판 프로브 (부수 결과)

`results/cal/tabular-b`(상위 모델 n=3): **0/3 실패, 세 세션 성능이 정확히
0.6159로 동일**, 73~82초, 최종 출력 토큰 1,513~1,868. 힌트가 있던 조건
(`ml-shift`, 보정 3 + 미기록 배치 7 = 10세션)은 성공 5, 249~455초.

힌트를 빼면 세 세션 모두 **조사를 아예 하지 않고** 전체 피처를 그대로 써서
함정에 빠졌고 서로 완전히 동일했다. 즉 `ml-shift`에서 관측된 세션 간 변동은
코딩 실력 차이가 아니라 **"프롬프트에 있는 단서를 집어 행동으로 옮기는가"의
차이**였다.

선등록한 기준은 문자적으로 중립판 채택을 가리키지만, 중립판은 변동 자체가
없어 능력 축 표본으로 쓸 수 없다. 역으로 힌트 있는 조건이 재고 있던 것이
"단서 포착의 세션 간 변동"이라면 설계 의도와는 다르나 유저의 원래 현상
서술에는 더 가깝다. **본 수집 조건 확정은 유저 승인 대기**(두 해석과 판정
근거는 STATUS 결정 로그에 선등록됨).

## 4. 다음 세션이 결정해야 할 것

설계 문제이므로 측정으로 답하지 말 것. 순서대로:

1. **채점 제약을 우회하는 방법을 먼저 정한다.** 판단·정합·규율을 결정론으로
   채점하려면 "두 해석이 서로 다른 검사 가능한 산출물을 낳도록" 과제를 짜서
   "알아챘는가"를 "어느 산출물을 냈는가"로 환원하는 방식이 후보다. 판단을
   직접 채점하지 않으므로 설계 원칙(결정론 코어, 프롬프트 강제 금지, 심판
   모델 금지)과 충돌하지 않는다.
2. **사전 상태 정합 과제군**을 그 방법으로 설계한다 — 상태 기록과 코드가
   어긋나 있거나 두 문서가 서로 다른 값을 명세하는 저장소. 유저 실경험에
   가장 가깝고, 이 프로젝트 자체가 정답 사례를 갖고 있다(오늘 발견한 미기록
   배치, 상태 기록 이력, 커밋 로그).
3. **기술적 실패 분리 규칙을 명문화한다** — 산출물 없음·시간 초과·퇴화 루프를
   능력 실패와 따로 집계. 확정 전까지 `results/main2/ml-shift-sonnet`은
   "3/6 + 기술적 실패 1"로 표기.
4. 위가 정해진 뒤에야 표본을 늘린다. 표 분류 조건은 회수 가능 잔액 54%로
   유일하게 유망하나 힌트 해석이 먼저 정해져야 한다.
