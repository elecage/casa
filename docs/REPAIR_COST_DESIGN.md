# 늦게 발견된 결함을 고치는 값을 어떻게 재는가 (2026-08-23, 유저 결정)

## 무엇을 고쳤나

유저 지적(2026-08-23): 거짓 완료 기록의 실제 값은 **에이전트가 그것을 알아서
찾아내는 것**이 아니라 **사람이 한참 뒤에 찾아내고 그때부터 치르는 값**이다.
사슬 안에서 뒤 세션이 발견하는지를 재면 그것은 "잘못된 결과를 찾아내는
에이전트 성능"을 재는 것이고, 유저가 알고 싶은 것과 다르다.

**그 지적이 맞다. 그래서 재는 것을 바꾼다.**

| | 앞서 하려던 것 | 바꾼 뒤 |
|---|---|---|
| 재는 것 | 뒤 세션이 거짓 완료를 발견하는가 | **발견 뒤 고치는 값이 발견 시점에 따라 얼마나 다른가** |
| 사람의 자리 | 없음(에이전트가 발견) | **발견 시점 하나** |
| 장치 | 초반 10호출에 끊는 훅 | **인계 검문**(아래 6절) |

**"발견하는가"를 재지 않는 이유가 하나 더 있다.** 그 질문은 이미 닫혔다 —
`docs/CLAIM_GAP_RESULTS.md`. 세션의 95%가 완료를 주장하고 그중 51%가
거짓인데, 주장 직전에 검증을 실행한 세션이 99%였다. 행동 신호 여덟 종이
전부 무신호였고 결론은 "구조적 한계이지 신호를 더 찾으면 되는 문제가
아니다" 였다. 그것을 다시 여는 것은 이 프로젝트가 기록해 둔 반복된 실수
5번과 같은 모양이다.

## 1. 가설

**같은 결함이라도 늦게 발견될수록 되돌리는 값이 크다.**

이 문장에서 사람은 **발견 시각**으로만 들어온다. 어떤 눈으로 어떻게
알아챘는지는 값에 안 들어간다. 그래서 모사해야 하는 것은 발견 과정 전체가
아니라 **발견이 일어나는 시점**이다.

## 2. 발견자는 이미 있다 — 채점기다

`grade.py` 는 숨은 표본으로 판정하고, 세션은 그것을 볼 수 없으며, 세션이
끝난 뒤에 적용된다. **바깥에서, 나중에, 세션이 못 보는 것으로 판정한다** —
사람이 하는 일과 같은 자리다.

사슬 프로브에서 그것이 12항목을 잡아냈다. 저장소 안에서는 체크박스 23개가
전부 채워져 있었고 보이는 테스트 18개가 다 통과했다. **탐지는 이미 모사되어
있고, 모사가 안 된 것은 발견 뒤에 치르는 값이다.**

## 3. 무엇을 견주는가 — 같은 결함, 발견 시점 둘

사슬 프로브(`results/probe/record-shape-chain`)에서 세션 2가 세션 1이
통과시킨 v0.3 항목 둘을 떨어뜨렸다. 그 둘은 사슬이 끝날 때까지 안 고쳐졌다.

| | 시작 상태 | 그 위에 쌓인 것 |
|---|---|---|
| **이른 수리** | 세션 2가 끝난 시점의 작업 트리 | 거의 없다 |
| **늦은 수리** | 세션 40이 끝난 시점의 작업 트리 | v0.4·v0.5 전체와 세션 38개 |

**수리 목표는 두 자리에서 똑같다** — 떨어진 그 항목 둘을 다시 통과시키고
다른 항목을 떨어뜨리지 않는 것. 프로젝트를 완성하는 것이 아니다.

**값은 수리에 든 호출 수와 세션 수다.** 늦은 쪽이 이른 쪽보다 크면 가설이
성립한다.

## 4. 수리 세션에 무엇을 주는가

**사람이 실제로 건네는 것을 준다 — 증상이지 진단이 아니다.**

주는 것: "9월치를 돌렸더니 읽어 들인 기록 수가 원천 파일의 줄 수와 맞지
않는다. 어느 줄이 빠졌는지도, 건너뛴 것으로 보고되지도 않는다."

주지 않는 것: 어느 어댑터가 문제인지, 어느 커밋에서 생겼는지, 어떻게
고치는지.

**앵커의 프롬프트 규칙 안쪽이다.** 증상은 "지금 무엇을 시키는지" 이고, 진단과
고치는 방법은 "무엇이 문제인지·어떻게 고칠지" 라서 안 넣는다. 실제 버그
보고가 증상을 적는다는 점에서 현실성 기준에도 맞다.

## 5. 무엇을 세는가

수리 자리마다 아래를 남긴다.

| | |
|---|---|
| 수리에 든 호출 수 | 1차 지표 |
| 수리에 든 세션 수 | 한 세션에 못 끝내는 경우 |
| 고쳐졌는가 | `regressions` 의 그 항목이 다시 통과하는가 |
| 다른 것을 깨뜨렸는가 | 수리하다 새로 떨어진 항목 |
| 지금 되돌리면 따라 바뀔 자리 | `detect.py` 의 `reversal_cost_at` |

**"다른 것을 깨뜨렸는가"를 반드시 같이 센다.** 늦은 수리가 호출을 적게 쓰고
끝났는데 다른 항목을 떨어뜨렸다면 그것은 싸게 고친 것이 아니다.

## 6. 이것이 맞으면 장치도 바뀐다

지금 장치는 **초반 10호출**을 본다. 그런데 사슬 프로브에서 값을 만든 세션은
세션 2이고, 그 세션은 항목을 두 번째로 많이 늘렸으며, 나쁜 점은 **자기가 한
일을 다 됐다고 적은 것**이다. 초반에 보이지 않고 끝날 때 나타난다.

그러면 장치는 초반 훅이 아니라 **인계 검문**이 된다 — 세션이 끝날 때 바깥
검사를 돌려 사실과 다른 완료 기록이 다음 세션으로 넘어가는 것을 막는 것.
시행을 코드에 두는 설계 원칙과 맞고, 이득도 위와 같은 수리 비용 단위로
잴 수 있다.

**이 프로젝트가 자기 세션에 쓰는 `harness/handoff_check.py` 가 정확히 그
장치다.** 우리가 우리에게 이미 걸어 둔 것을 측정 대상에도 걸어 보는 것이다.

## 7. 이 설계가 재지 못하는 것

- **사람의 시간은 안 나온다.** 우리가 세는 것은 에이전트의 수리 비용이다.
  사람이 코드를 다시 읽고 무엇이 벌어졌는지 재구성하는 값은 이 설계로 안
  나온다.
- **그래서 옮겨지는 것은 절대값이 아니라 비율이다** — 늦은 수리가 이른
  수리의 몇 배인가. 보고할 때 이 한정을 빼면 안 된다.
- **발견 시점을 우리가 정한다.** 실제로는 발견이 언제 일어날지가 확률적이다.
  이 설계는 "만약 그때 발견됐다면" 을 잰다.
- **결함이 하나다.** 사슬 프로브가 만든 그 결함으로 시작한다. 결함의 종류에
  따라 값이 다를 수 있다.

## 8. 실행 조건 (유저 승인 뒤)

| | |
|---|---|
| 시작 상태 | 스냅숏 저장소에서 두 시점의 작업 트리를 꺼내 쓴다 |
| 자리마다 세션 수 | 최대 3(한 세션에 못 끝낼 수 있다) |
| 예산 | 세션당 100 |
| 되풀이 | 자리마다 5회 — 세션 사이의 폭이 크므로 한 번으로는 못 견준다 |
| 규모 | 2자리 × 5회 × 최대 3세션 = 최대 30세션 |
| 비용 예상 | $10~15 |

**되풀이 5회는 관측 하한 8에 못 미친다.** 그래서 이 실행의 결과는 "판정" 이
아니라 **다음 배치에서 봉인할 예측의 근거**다. 그 한정을 결과 문서 첫 줄에
적는다.
