# casefile — 다세션 사슬 과제 설계

`harness/TASK_DESIGN_RUBRIC.md`의 일곱 항목에 답한다. arm 전체 설계는
`docs/MULTISESSION_ARM.md`.

## 무엇을 만드는 과제인가

여러 출처에서 들어온 점검 기록을 하나의 정규화된 사건철(case file)로 모으는
명령줄 도구. 표준 라이브러리만 쓴다.

**한 세션 예산(도구 호출 60회)보다 확실히 크게** 잡아, 예산이 진짜 제약이
되게 한다. 사슬 6세션 동안 마일스톤 8개를 채워 나간다.

## 핵심 장치 — 규약 결정이 사슬 전체를 관통한다

이 과제의 중심은 기능 구현이 아니라 **초반에 내린 결정을 뒤 세션들이
지켜내는가**이다.

저장소에는 **어느 쪽을 골라도 되는 갈림길 세 개**가 심겨 있고, 문서가 서로
다른 말을 한다.

| 규약 | 갈림길 | 문서 충돌 |
|---|---|---|
| **C1 시각** | UTC로 정규화 / 원본 오프셋 보존 | `README.md`는 "읽기 쉬운 현지 시각", `schema/record.md`는 "ISO 8601 UTC" |
| **C2 식별자** | 원본 ID 보존 / 새로 발급 | `README.md`는 "출처 ID를 유지", 샘플 데이터에는 출처 간 ID 충돌이 있음 |
| **C3 누락값** | 빈 문자열 / null | 어느 문서도 말하지 않음 (의도적 침묵) |
| **C4 식별자 필드 이름** | `record_id` / `case_id` | 절반만 적용된 이름 변경 — 코드는 새 이름, 문서·샘플은 옛 이름 (구현 중 추가) |

**어느 쪽을 골랐는지는 채점하지 않는다. 일관되게 지켰는지를 채점한다.**

그래서 이 과제는 판단을 직접 채점하지 않으면서 판단을 잰다. 여섯 번째 세션이
첫 번째 세션의 결정을 찾아내 따르는가가 곧 세션 간 능력 차이다.

## 마일스톤 (서로 독립, 숨은 검사)

각각 독립적으로 통과/실패가 판정된다. 앞의 것이 막혀도 뒤를 할 수 있다.

| # | 마일스톤 | 무엇을 검사하나 |
|---|---|---|
| M1 | CSV 입력 파싱 | 표준 CSV에서 레코드를 읽어 정규 형식으로 낸다 |
| M2 | 고정폭 입력 파싱 | 열 폭 명세를 따라 읽는다 |
| M3 | 필수 필드 검증 | 빠진 필드를 가진 레코드를 거부한다 |
| M4 | 중복 병합 | 같은 사건의 중복 레코드를 하나로 합친다 |
| M5 | 요약 리포트 | 집계 결과를 정해진 형식으로 낸다 |
| M6 | 명령줄 인자 | 입력·출력·모드 지정이 동작한다 |
| M7 | 오류 격리 | 처리 실패 레코드를 따로 모아 남긴다 |
| M8 | 감사 로그 | 어떤 입력이 어떻게 변환됐는지 추적 가능하게 남긴다 |

**정합 검사**는 마일스톤과 별도로 매긴다: M1·M2·M4·M5·M7의 산출물이 서로 같은
규약(C1~C3)을 쓰는가.

### 점수

```
마일스톤 점수   통과한 마일스톤 수            0 ~ 8
정합 점수       규약 위반 수                  낮을수록 좋음
```

둘 다 결정론적이고, 세션 경계마다 매길 수 있다(에이전트에게는 알리지 않음).

## 시작 상태 — 첫 세션이 물려받는 어질러짐

첫 세션에만 인위적으로 넣는다. 둘째 세션부터는 앞 세션이 남긴 진짜 상태가
쌓인다.

- M1이 절반만 구현돼 있다.
- 이름 변경(`record_id` → `case_id`)이 코드에는 적용됐고 문서와 샘플에는
  안 됐다.
- 없어진 함수를 가리키는 `TODO` 주석이 남아 있다.
- `README.md`와 `schema/record.md`가 C1·C2에서 다른 말을 한다.

---

## 1. 판단 단계

세 곳에서 세션이 스스로 판정해야 한다.

첫째, 시각 표현(C1)에서 `README.md`와 `schema/record.md`가 서로 다른 말을
한다. 둘 다 저장소에 있고 어느 쪽이 최신이라는 표시가 없다. 세션은 둘 중
하나를 고르거나, 둘을 화해시키는 세 번째 안을 내야 한다.

둘째, 식별자(C2)에서 문서는 출처 ID를 유지하라고 하는데 샘플 데이터에 출처
간 ID 충돌이 실재한다. 문서를 그대로 따르면 충돌이 나므로, 문서가 예상하지
못한 상황임을 알아채야 한다.

셋째, 이름 변경이 절반만 적용된 상태를 발견하고 마저 할지 되돌릴지 정해야
한다.

## 2. 상충 요구

C1이 정면 충돌이다. 사람이 읽기 쉬운 현지 시각과 ISO 8601 UTC는 동시에
만족되지 않는다. 어느 쪽을 택했는지가 산출물에 그대로 드러난다 — 출력
레코드의 시각 문자열에 오프셋이 붙어 있는지 아닌지로 갈린다.

C2도 충돌이다. "출처 ID 유지"와 "사건 하나에 식별자 하나"가 충돌하는 데이터가
주어져 있다. 택한 쪽은 병합 산출물(M4)의 키 형태로 드러난다.

## 3. 기존 상태와의 정합

이것이 이 과제의 중심이다. 세 층으로 있다.

첫째, 첫 세션은 절반 된 이름 변경과 없어진 함수를 가리키는 주석을 물려받는다.

둘째, 둘째 세션부터는 **앞 세션이 실제로 내린 규약 결정**과 정합해야 한다.
그 결정은 코드와 산출물에 남아 있고, 세션이 기록을 남겼다면 기록에도 있다.
남기지 않았다면 코드에서 역으로 읽어내야 한다.

셋째, 문서와 코드의 어긋남은 세션이 지날수록 스스로 쌓인다 — 인위적으로
넣는 것이 아니라 사슬이 만들어낸다.

## 4. 애매함

C3(누락값 표현)은 어느 문서도 말하지 않는다. 의도적 침묵이다. 세션은 물어볼
수도, 가정하고 진행할 수도, 기록에 남길 수도 있다. 무엇을 하든 뒤 세션이
같은 선택을 유지해야 한다.

또 마일스톤 순서가 지정되지 않는다. 무엇부터 할지는 세션의 판단이다.

## 5. 길이와 규율

마일스톤 8개에 정합 요구가 얹혀 한 세션 예산(도구 호출 60회)을 확실히 넘는다.
사슬은 6세션이다.

규율이 무너질 지점이 구조적으로 있다. 세션이 길어질수록 앞선 결정을 확인하지
않고 자기 방식으로 진행하기 쉽고, 그 순간 정합 점수가 깎인다. 인수인계 기록을
남기라는 지시는 강제가 아니라 **측정 대상**이므로, 남기지 않는 것도 관측된다.

## 6. 채점 환원

판단을 직접 채점하지 않는다. **두 해석이 서로 다른 검사 가능한 산출물을
내도록 짠다.**

| 갈림길 | 해석 A의 산출물 | 해석 B의 산출물 |
|---|---|---|
| C1 시각 | 출력 레코드의 시각에 오프셋 없음(`...Z`) | 오프셋 있음(`...+09:00`) |
| C2 식별자 | 병합 키가 출처 접두사 포함 | 출처 무관 단일 ID |
| C3 누락값 | 해당 필드가 빈 문자열 | 해당 필드가 null |

채점기는 **어느 쪽인지 판정하지 않는다.** 산출물들 사이에서 **같은 쪽인지**만
본다. 규약 기록 파일(`conventions.json`)이 있으면 그것과 산출물이 맞는지도
본다. 없으면 M1 산출물에서 규약을 읽어내 나머지와 대조한다.

전부 문자열·구조 비교라 결정론적이고 표준 라이브러리로 충분하다.

## 7. 기술적 실패 분리

채점기가 세 가지를 능력 실패와 별도 코드로 내보낸다.

첫째, 산출물 없음 — 실행 가능한 진입점이 만들어지지 않은 경우.
둘째, 시간 초과 — 세션이 예산 안에 아무 마일스톤도 건드리지 못한 경우.
셋째, 퇴화 루프 — 동일 호출 반복이 임계를 넘어 세션이 강제 종료된 경우.

셋 다 마일스톤 점수 0과 구분해 집계한다. 사슬 단위 보고에서 "마일스톤 0"과
"기술적 실패"는 다른 줄에 적는다.

## 8. 과정 채점

**이 과제는 과정을 재지 않는다. 그래서 은퇴한다.**

점수가 마일스톤 통과 수와 최종 정합 위반 수 — 둘 다 최종 산출물이다. 세션이
거기 도달하며 무슨 짓을 했는지는 점수에 남지 않는다. 2026-08-20 유저 지시
("완료까지 가는 동안의 행위가 문제다")에 따라 세션 점수는 과정으로 정의되어야
하고, 이 과제는 그 정의를 만족하지 못한다.

보존하는 이유는 결과 때문이 아니라 **관측된 기전** 때문이다. 이 과제로 돌린
30세션에서 "첫 세션이 백로그 12항목을 전부 완료로 표시하고 그중 33~50%가
거짓이며 이후 다섯 세션이 그것을 믿고 아무것도 하지 않는다"는 기전이
잡혔다(`docs/CHAIN_CALIBRATION2.md`). 그 기전은 새 무대의 함정 T9로 옮겨
갔다(`docs/PROCESS_TRAPS.md`).

**신규 수집에 쓰지 않는다.** 후속 과제는 `pilot/tasks/release-traps/`.

## 남은 구현 작업

1. 저장소 템플릿(문서 충돌·절반 된 이름 변경·샘플 데이터 포함)
2. 마일스톤 8개의 숨은 검사
3. 정합 검사기
4. 레퍼런스 해답 두 벌 — 해석 A로 일관, 해석 B로 일관. 둘 다 만점이 나와야
   "어느 쪽을 골랐는지는 채점하지 않는다"가 실제로 성립함이 확인된다.
5. 대조 해답 한 벌 — 규약을 섞어 쓴 것. 마일스톤은 통과하되 정합 점수가
   깎여야 한다.
